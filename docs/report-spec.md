# 報告規格

原始格式檔：`docs/format/midterm-proposal-format.pdf`、`docs/format/final-project-format.pdf`。以下是整理後的內容與建議大綱。

## 共同格式

- 字型：中文**標楷體**；英文與符號 **Times New Roman**
- 邊界：上下左右各 **1.2 公分**
- 參考文獻格式依老師範例（等同 Google Scholar 的 MLA 引用格式）：

```
[1] Madakam, Somayya, et al. "Internet of Things (IoT): A literature review." Journal of Computer and Communications 3.05 (2015): 164.
```

## 期中：研究計畫書（Project proposal）

**總頁數必須剛好 25 頁，不能多也不能少。**

格式要求的章節與配分：

- 一、研究計畫之背景及目的（30%）
  1. 背景、目的、重要性
  2. 國內外相關研究情況與重要參考文獻之評述（參考文獻必須條列，依範例格式）
- 二、研究方法、進行步驟及執行進度（60%）
  1. 本計畫採用之研究方法與原因（**共計 19 頁，不能多也不能少**）
  2. 預計可能遭遇之困難及解決途徑
- 三、預期完成之工作項目、成果及績效（10%）
  1. 預期完成之工作項目
  2. 對於學術研究、國家發展及其他應用方面預期之貢獻

**2026-10-14 使用者決定：有封面＋目錄，兩者都算在 25 頁內。** 所以正文＋參考文獻列表共 **23 頁**，其中「二、1. 研究方法與原因」剛好 19 頁，其餘（一、二.2、三）合計 4 頁。下方舊的頁數分配以 `report/midterm/00-outline.md` 為準。

### 建議大綱與頁數分配（假設參考文獻列表計入、無封面）

**一、背景及目的（約 4.5 頁）**

1. 背景、目的、重要性（約 2 頁）
   - 雲端 API 的隱私、成本、離線限制；開源模型快速進步但消費級硬體 VRAM 有限
   - 列出 RQ1～RQ3（見 CLAUDE.md）
   - 重要性：讓學生、小型組織以平價硬體建立私有 AI 服務
2. 文獻評述（約 1.5 頁）＋參考文獻列表（約 1 頁），依主題分段：
   - 模型架構：Transformer、GQA、FlashAttention
   - 量化技術：GPTQ、AWQ、llama.cpp 的 k-quants／i-quants、imatrix
   - 新型架構：MoE、混合線性注意力（Gated DeltaNet）
   - 推論系統與效能模型：llama.cpp、vLLM（PagedAttention）、Roofline
   - 工具使用：ReAct、Toolformer、MCP
   - 邊緣運算（與指導教授的無線網路方向呼應，選擇性加入）

**二、研究方法、進行步驟及執行進度**

2.1 研究方法（剛好 19 頁）：

| 小節 | 內容 | 頁數 |
|---|---|---|
| 2.1.1 研究架構總覽 | 整體流程圖：部署 → 量測 → 分析 → 應用驗證 | 1 |
| 2.1.2 實驗環境 | 兩台機器規格表、OS、驅動、部署方式（Docker 映像、build 編號） | 2 |
| 2.1.3 模型選擇 | 為何選 Qwen3.8-27B；架構特性（混合注意力每 4 層 1 層全注意力、GQA、MTP 層） | 2 |
| 2.1.4 量化方法 | 量化原理、GGUF、bpw、imatrix、Unsloth Dynamic 混合精度（引用 log 中的 tensor 類型分布） | 2.5 |
| 2.1.5 記憶體需求分析 | 權重、KV cache、遞迴狀態、運算暫存的公式，並以實際 log 驗證（見 findings） | 3 |
| 2.1.6 推論效能理論分析 | prefill 受限於運算、decode 受限於記憶體頻寬；Roofline 推估理論上限並與實測比較 | 2 |
| 2.1.7 實驗設計 | 自變數、應變數、控制變數、工具、資料集、重複次數（見 experiment-plan） | 3 |
| 2.1.8 應用案例設計 | MCP 網頁搜尋架構、時效性問題集、計算工具與「600 vs 601」案例 | 1.5 |
| 2.1.9 初步結果 | findings 中已有的實測數據整理成表 | 1.5 |
| 2.1.10 執行進度 | 到期末的甘特圖 | 0.5 |

2.2 預計遭遇之困難及解決途徑（約 1 頁），使用使用者真實遇過的問題：
- VRAM 不足 → 權重量化、KV cache 量化、視覺模組移至 CPU、螢幕改接內顯釋放 VRAM
- 長時間推理耗盡 context → 擴大 context、限制思考預算、關閉 reasoning preserve
- 遠端連線中斷導致服務終止 → 容器化常駐部署
- 運算後端不符（winget 版為 Vulkan 而非 CUDA）→ 部署後先以 `--list-devices` 驗證
- 模型輸出不可靠（大數運算錯誤、題意誤解）→ 以標準答案程式化批改，不直接採信

**三、預期工作項目、成果及績效（約 1 頁）**
1. 預期工作項目：完整效能數據、量化與品質權衡分析（Pareto 前緣）、不同 VRAM 的部署建議、MCP 應用評估
2. 預期貢獻：學術（混合架構模型在消費級硬體的實測數據）、國家發展（資料主權與個資保護）、應用（低成本私有 AI 服務）

## 期末：Final Project

無頁數規定。章節與配分：

- 一、研究方法、進行步驟（70%）：沿用並更新期中的研究方法章節，改為「已執行」的敘述
- 二、執行結果（30%）：效能分析或專案執行結果

### 執行結果建議安排

1. 速度：量化 × 硬體 × prompt 長度的對照表與圖
2. 記憶體：實測 VRAM 用量與公式預測值比對
3. 品質：各量化等級的困惑度（＋選配的 KL 散度）
4. 任務正確率：兩組題目的答對率與信賴區間
5. 權衡分析：速度 vs 品質散布圖，標出 Pareto 前緣；給出 12GB／16GB 的建議設定
6. 應用案例：MCP 搜尋對時效性問題正確率的影響；計算工具對算術錯誤的修正
7. 限制與未來工作

## 寫作風格

- 學術計畫書語氣，第一人稱用「本研究」「本計畫」
- 每張圖表都要有編號、標題，並在內文中引用
- 實測值與推導值分開標示；表格註明資料來源（log 檔名或 results 檔名）
- 不要寫出比數據更強的結論；樣本數少時明講

## 產生 Word 檔

1. 草稿以 Markdown 寫在 `report/midterm/` 或 `report/final/`，每節一個檔案方便審閱
2. 使用者確認內容後，用 `python-docx` 產生 .docx：
   - 邊界 1.2 cm
   - 字型：西文設 `Times New Roman`，東亞字型設 `標楷體`（需透過 `rPr` 的 `w:eastAsia` 屬性設定，python-docx 的 `font.name` 只會設西文）
   - 標題、內文、表格、圖說使用一致的樣式
3. 頁數驗證：用 LibreOffice 轉 PDF 後計算頁數（`soffice --headless --convert-to pdf`，再用 `pdfinfo` 讀頁數）。注意 LibreOffice 若沒有標楷體會用替代字型，頁數可能和 Word 略有差異，**最終頁數以使用者在 Word 開啟後為準**，交件前請使用者確認
4. 頁數微調：先把內容寫完，最後再用圖表大小、段距調整到剛好 25 頁，研究方法章節剛好 19 頁
