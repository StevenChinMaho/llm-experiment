### 2.1.5 記憶體需求模型（E2）

**為什麼需要記憶體模型。** 推論引擎在啟動時一次配置所有記憶體，之後對話變長也不會再增加；放不下時，Linux 上會直接配置失敗。因此「某個設定能不能跑」完全取決於啟動時的配置量。若能用公式事先算出配置量，使用者就不必反覆嘗試。本研究以 `-lv 4` 讓推論引擎在啟動紀錄中列出每一塊記憶體，再與公式比對。

**組成。** 啟動紀錄中 GPU 上的記憶體分為四塊：權重、KV cache、遞迴狀態，以及運算暫存（compute buffer，存放計算中間值）；另有 token embedding 留在系統記憶體（IQ3_XXS 為 397.85 MiB）。

**KV cache 公式。** 每個 token 的 KV cache 為：

> 有 KV cache 的層數 × (K 維度 ＋ V 維度) × 每元素位元組數 ＝ 16 × (1,024 ＋ 1,024) × 1.0625 ＝ 34,816 bytes ＝ **34 KiB**

其中 K、V 維度各為 4 個 KV head × 256；q8_0 格式每 32 個元素存 32 個 8 位元整數加 1 個 16 位元縮放係數，即 34 bytes，平均每元素 1.0625 bytes。若把模型當成 64 層全注意力、KV 以 16 位元儲存的傳統 Transformer，同樣的估算會得到 256 KiB，高估約 7.5 倍。

**運算暫存與遞迴狀態。** 本研究在兩台機器上，對 4 種量化各以多個 context 長度啟動（固定點 4,096、16,384、32,768、65,536，以及二分搜尋過程中的點），共取得 51 組紀錄。結果如下（實測）：

1. **KV cache 與公式完全一致**：51 組的誤差全部為 0.00 MiB
2. **遞迴狀態固定為 149.62 MiB**，與 context 長度和量化等級無關
3. **運算暫存隨 context 線性成長**：context ≥ 16,384 時，各點都落在「80.28 MiB ＋ 5 KiB × context」這條直線上，殘差為 0（此式為本研究由數據擬合，屬推導值；context 4,096 時為 126.28 MiB，高於直線，推測有最低配置量）
4. nvidia-smi 顯示的用量比上述四項加總固定多出一段 CUDA 本身的開銷，RTX 3060 約 146 MiB、RTX 5060 Ti 約 174 MiB

由此得到簡單的記憶體模型（context ≥ 16,384）：

> GPU 用量 ≈ 權重 ＋ 149.62 MiB ＋ 80.28 MiB ＋ CUDA 開銷 ＋ **39 KiB × context**

每多一個 token 的 context 只多用 39 KiB（KV 34 KiB ＋ 運算暫存 5 KiB）。以 16GB 卡為例，1 GiB 的 VRAM 約等於 2.7 萬個 token 的 context。

**最大 context。** 本研究以二分搜尋（解析度 1,024 token）找出每種設定在全部放入 GPU 時能啟動的最大 context（表 4）。成功的定義是能啟動、全部的層都在 GPU 上，且能完成一次推論。

**表 4　全部放入 GPU 時的最大 context（實測）**

| 量化 | RTX 3060 12GB | RTX 5060 Ti 16GB |
|---|---|---|
| UD-IQ2_XXS | 131,072 | 233,728 |
| UD-Q2_K_XL | 75,520 | 178,432 |
| UD-IQ3_XXS | 48,384 | 151,040 |
| UD-IQ4_XS | 放不下 | 70,400 |

**預測驗證。** 為檢驗模型的實用性，本研究在主力機實驗前，先用 RTX 3060 上歸納出的模型預測 RTX 5060 Ti 跑 IQ4_XS 的最大 context，得到 71,909（推導值）；實測為 70,400，預測高估約 2%。誤差主要來自兩張卡的 CUDA 開銷不同。換言之，使用者只需要知道權重大小與顯示卡可用的記憶體，就能在 2% 左右的誤差內預估可用的 context。

**初步發現（RQ2）。** 表 4 顯示，在 12GB 卡上把量化從 IQ3_XXS 降到 IQ2_XXS，最大 context 從約 4.8 萬增加到 13.1 萬（2.7 倍）；在 16GB 卡上從 IQ4_XS 降到 IQ3_XXS，則從約 7 萬增加到 15 萬。降低權重精度換來的 context 容量非常可觀，但品質代價要配合 2.1.7 一起看。

**後續工作。** KV cache 精度（16 位元／q8_0／q4_0）也會改變每 token 的成本（推導值分別為 64／34／18 KiB），若時間允許，將以 KL 散度評估它對品質的影響（延伸實驗）。

### 2.1.6 推論效能量測（E1）

**理論：兩個階段受不同的資源限制。** LLM 推論分為兩個階段。**讀取 prompt（prefill）**一次處理數百個 token，每讀一次權重可以做大量運算，速度主要受 GPU 運算能力限制。**生成（decode）**每產生一個 token 都要把全部權重從記憶體讀一遍，運算量相對很少，速度主要受**記憶體頻寬**限制。依 Roofline 模型 [9]，生成速度的理論上限約為「記憶體頻寬 ÷ 權重大小」。因此權重越小，生成應該越快；這是量化除了省記憶體之外的另一個好處。

**方法。** 使用 llama-bench 量測讀取 512 個 token 的速度（pp512）與生成 128 個 token 的速度（tg128），並在 context 深度 0、4,096、16,384、32,768 下各量一次，以觀察 context 變長時的速度變化。部分卸載的設定則掃描放在 GPU 上的層數。另由數據推算兩個衍生指標：**頻寬使用率**（權重大小 × 生成速度 ÷ 理論頻寬，推導值）與**每 token 能耗**（GPU 功耗 ÷ 生成速度，推導值，只含 GPU）。

**表 5　生成速度（tok/s，實測，llama-bench 5 次平均；括號內為頻寬使用率，推導值）**

| 量化 | 5060 Ti 深度 0 | 5060 Ti 深度 32K | 3060 深度 0 | 3060 深度 32K |
|---|---|---|---|---|
| UD-IQ2_XXS | 41.36（67%） | 32.08 | 24.37（49%） | 18.69 |
| UD-Q2_K_XL | 35.38（78%） | 28.53 | 22.38（61%） | 17.57 |
| UD-IQ3_XXS | 32.82（80%） | 26.87 | 21.44（65%） | 16.89 |
| UD-IQ4_XS | 27.92（89%） | 23.57 | 8.88（部分卸載 56 層） | — |
| UD-Q4_K_XL | 17.49（部分卸載 62 層） | — | — | — |

標準差都小於平均值的 1%。讀取 prompt 的速度在 5060 Ti 上為每秒 889～970 token、3060 上為 526～543 token（全部放入 GPU 時）。

**圖 2　權重大小與生成速度（左）；部分卸載時 GPU 上的層數與生成速度（右）**

**初步發現。**

1. **5060 Ti 上量化越低越快，3060 上幾乎沒有差別。** 5060 Ti 從 IQ4_XS 降到 IQ2_XXS 快了 48%；3060 從 IQ3_XXS 降到 IQ2_XXS 只快 14%，頻寬使用率從 65% 降到 49%。表示在 3060 上，權重小到一定程度後，瓶頸已不完全是記憶體頻寬（推測與運算能力或快取有關，待驗證）。對 12GB 卡的使用者而言，降低量化換到的主要是 context 容量（2.1.5），而不是速度
2. **兩張卡的速度差距大於頻寬差距。** 理論頻寬比為 1.24，實測生成速度比為 1.53～1.70，且量化越低差距越大，與上一點一致
3. **部分卸載是一道懸崖。** 3060 跑 IQ4_XS 時最多只能放 56 層在 GPU 上，生成速度只有 8.88 tok/s，比全部放入 GPU 的 IQ3_XXS 慢 59%；5060 Ti 跑 Q4_K_XL（62 層）為 17.49 tok/s，比 IQ4_XS 慢 37%。GPU 上每少 2～4 層，速度再掉約 0.8～2.0 tok/s（圖 2 右）
4. **context 越深越慢。** 深度 32K 時生成速度比深度 0 慢 16～23%，這是每個 token 都要讀取更長 KV cache 的結果
5. **能耗。** 全部放入 GPU 時，5060 Ti 每 token 約 4.4～6.4 J、3060 約 7.0～7.9 J（推導值）；部分卸載時 3060 上升到 10.5～12.1 J

這些結果說明，「能不能完整放進 GPU」比「量化等級高一級」對速度的影響大得多，是 RQ2 部署建議的主要依據。
