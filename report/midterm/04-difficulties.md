## 2. 預計可能遭遇之困難及解決途徑

以下困難多數已在初步實驗中實際遇到，解決途徑也已驗證。

| 困難 | 解決途徑 |
|---|---|
| **VRAM 不足**：27B 模型以 16 位元儲存需 51 GiB | 權重量化；KV cache 以 q8_0 儲存；不需要時不載入視覺模組；關閉獨顯的螢幕輸出；以 2.1.5 的記憶體模型事先估算 |
| **作業系統默默超用記憶體**：Windows 允許配置超過 VRAM，把溢出部分放到系統記憶體。實測在 context 83,536 時讀取 prompt 的速度只剩正常的 8～39%，生成速度卻不變，只看生成速度的使用者不會察覺 | 正式實驗只在 Linux 上進行，放不下時直接配置失敗，界線明確；在 Windows 上則以效能計數器的「共享 GPU 記憶體」監看是否溢出 |
| **兩台機器的軟體版本不同**：初期一台用 conda 版（build 10751）、一台用 Docker 版（build 11347） | 兩台都改用 Docker，並以映像 digest 固定同一個 build；驅動也統一版本 |
| **思考無上限而耗盡 context**：曾有一題思考約 8.2 萬 token 仍未作答 | 以 `--reasoning-budget` 限制思考長度，並保留足夠的作答空間 |
| **模型輸出與資料本身都可能出錯**：模型會算錯長數字；公開資料集也發現 2 題題目抄寫錯誤 | 一律以程式批改；標準答案以獨立程式或第二份資料來源交叉驗證 |
| **推測解碼在執行中途記憶體不足**：n_max 過大時能啟動、卻在第一次推論時中止 | 以 2.1.8 量到的遞迴狀態公式事先計算，並限制 n_max |
| **題目太簡單（天花板效應）**：校準時答對率達 90～100% | 以思考預算與量化等級作為主要自變數，使比較條件遠離天花板；同時保留自行設計的題目對照資料汙染 |
| **長時間實驗中斷**：遠端連線中斷會終止前景程式 | 所有長時間實驗以 nohup 或 Docker 背景執行，輸出即時寫入檔案，可中斷後接續 |
